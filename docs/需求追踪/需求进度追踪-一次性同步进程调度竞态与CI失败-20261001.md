# 需求进度追踪 - 一次性同步进程（run-sync-job）调度竞态导致 Backend Tests 间歇失败

## 1. 需求摘要
- 需求名称：修复 CI「Backend Tests」中 `internal/syncjob` 的 `TestEnqueueDueJobRunExecutesTargetRunToTerminal` 间歇失败
- 发现日期：2026-10-01（Backend Tests #1056、#1057 失败；#1055 通过，两次失败的提交均未改动 syncjob）
- 失败形态（同一用例两种）：
  - `manager_oneshot_test.go:62`：到期任务应被入队（`enqueued=false`）
  - `manager_oneshot_test.go:65`：入队运行状态 = `succeeded`，期望 `queued`
- 目标：消除竞态，使一次性执行的行为确定。
- 非目标：不改常驻主应用 / 常驻 worker 的调度行为。

## 2. 根因（本机 300 次重复运行复现 5 次）
- `NewManager`（非 Passive）启动后，`schedulerLoop` 的**首轮扫描在 ticker 之前立即执行**，会把所有到期任务入队并推进调度。
- 一次性进程 / 测试随后显式调用 `EnqueueDueJobRun`：
  - 后台先入队并推进调度 → 手动调用找不到到期任务，返回 `enqueued=false`；
  - 后台入队并已执行完 → 手动调用走 `GetRun` 取回已完成的运行，状态为 `succeeded`。
- 不只是测试问题：`RunScheduledJobOnce` 在 `enqueued=false` 时不等待运行结果、直接收尾；且一次性进程的调度循环会顺带处理其他到期任务（含持续型任务），与 `EnqueueDueJobRun` 注释「持续型任务由在线主应用的调度器负责，一次性进程不碰」的意图矛盾。

## 3. 修复
- 新增 `ManagerOptions.SchedulerDisabled`：保留派发与执行，不启动调度循环，入队完全由调用方决定。
- `internal/app/data_sync_worker.go` 的一次性进程管理器启用该选项，只执行 `EnqueueDueJobRun` 入队的那一个任务。
- 为不让存量超标的 `manager.go` 净增行数，把 `ManagerOptions` 与 `normalizeManagerOptions` 原样迁移到新文件 `manager_options.go`（`manager.go` 1166 → 1124 行）。
- 测试：既有用例按生产配置启用 `SchedulerDisabled`；新增用例证明调度器关闭的管理器不会自行入队到期任务（调度器强制开启时该用例失败）。

## 4. 验证记录
- 修复前：`-count=300` 复现 5 次失败（第 62 行）。
- 修复后：竞态用例与新增用例各 `-count=300` 全部通过；`go test ./internal/syncjob/` 通过；`go build ./internal/...`、`go vet ./internal/syncjob/` 通过；`internal/app` 内数据同步 worker / 挂起相关用例通过。
- 未验证：真实 OS 计划任务触发 `run-sync-job` 的端到端流程（需要真实计划任务环境）。

## 5. 风险与回滚
- 风险：一次性进程不再自行处理其他到期任务；这些任务由各自的 OS 触发器或在线主应用调度。调度租约仍在启动时获取以完成中断恢复，行为不变。
- 回滚：去掉 `newDataSyncJobManager` 中的 `SchedulerDisabled: true` 即恢复原行为（竞态随之回来）。
