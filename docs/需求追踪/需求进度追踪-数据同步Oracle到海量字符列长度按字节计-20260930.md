# 需求进度追踪 - 数据同步 Oracle → 海量（Vastbase）写入「值太长」

## 1. 需求摘要
- 需求名称：修复 Oracle 同步到海量（Vastbase）时报 `pq: 对于可变字符类型(120)来说，值太长了 (22001)`
- 提出日期：2026-09-30（用户反馈，本机无 Oracle / 海量环境，无法复现）
- 目标：定位根因并修复；不改数据同步的对外行为与后端契约。
- 非目标：不改已存在目标表的结构；不处理 Oracle / 达梦目标的同类字节计长问题（另行评估）。

## 2. 根因（推断，未能在真机复现）
- 海量（Vastbase）基于 openGauss：非 PG 兼容模式（默认的 A 兼容等）下 `varchar(n)` / `char(n)` 的 n 是**字节数**，PG 兼容模式才是字符数。
- 同步建表把源列长度原样下发：Oracle `VARCHAR2(120)`（`formatOracleColumnType` 只取 `CHAR_LENGTH`，丢掉 BYTE/CHAR 语义）→ 中间类型 `varchar(120)`（`toMySQLColumnType` 明确忽略 char/byte 语义）→ 目标 `varchar(120)`。
- 含中文的数据：源库按字符计长，或源库是 GBK（汉字 2 字节）而目标是 UTF-8（汉字 3 字节），落到「按字节计 120」的目标列就超长，报 22001。
- 同样的机制影响所有「字符计长源 → openGauss 系目标」的组合：MySQL / PostgreSQL / Kingbase / HighGo → Vastbase / openGauss / GaussDB。
- 错误信息里没有列名，且原来没有任何提示，用户无从判断是长度语义问题。

## 3. 修复
- 新增 `internal/sync/migration_byte_length_target.go`：目标为 vastbase / opengauss / gaussdb 且源不是同一族时，建表与补列把 `varchar(n)` / `char(n)`（含 `character varying(n)` 等写法）放宽为 4 倍（UTF-8 单字符最多 4 字节，上限 10485760），并汇总成一条告警（最多列 5 个字段）。同族之间语义一致，不放宽；PG / Kingbase / HighGo 等字符计长的目标不受影响。
- 接入点：跨方言自动建表（`buildCrossDialectAutoCreatePlan`，Oracle / SQL Server / 达梦 等源）、MySQL→PG 系建表、PG 系→PG 系建表、`buildAddColumnSQLForPair` 补列。
- 已存在的目标表无法自动改长度：在统一落库出口 `applySnapshotChanges` 对「目标按字节计长 + 值太长」的失败追加可操作提示（加宽相关列到源长度的 3~4 倍，或改用 PG 兼容模式库），保留原始错误链。新增文案 `data_sync.backend.hint.byte_length_overflow`（六语言）。

### 3.1 补充：用户实际用的是「数据同步」入口的差异同步（目标表已存在）
- 该入口目标表策略固定为「仅使用已有目标表」（`DataSyncModal.tsx` 非迁移入口强制 `existing_only`），目标表是用户已有的，上面的「建表/补列放宽」不会生效。
- 因此在统一落库出口 `applySnapshotChanges` 增加失败诊断（`sync_value_length_diagnosis.go`）：仅在写入报「值太长」（22001）且目标为按字节计长的库时，读取目标列定义，与本次待写入的新增/更新数据逐列比对，提示具体字段、声明类型、最长字节/字符数、超出行数和参考 `ALTER TABLE ... ALTER COLUMN ... TYPE varchar(n)`。
- 口径区分：字符数没超、字节数超 → 说明目标按字节计长，附口径说明；字符数本身就超 → 是数据比列长，不再归因于字节计长。
- 只在失败后运行，不会误拦成功的同步；读不到目标列定义时退回通用提示。新增 3 个文案键（六语言）。

### 3.2 补充：差异同步应能「把差异解决」——选了结构时允许建表（用户已确认方案）
- 现状：「数据同步」入口目标表策略被前端强制为 `existing_only`（只有「迁移」入口能自动建表）；缺字段在仅同步数据时被静默忽略。
- 决策（用户选择）：不改默认（仍是「仅同步数据」），但当同步内容选「仅同步结构 / 同步结构和数据」时，数据同步入口放开「目标表要求」下拉，缺表建表、缺字段补字段；「仅同步数据」仍固定为只用已有目标表（后端在该模式下禁止改结构，选了建表只会执行期失败）。
- 实现：新增 `dataSyncTableCreation.ts`（`isTargetTableCreationAllowed`）；`resolveDataSyncTargetTableStrategy` 增加 `syncContent` 参数（数据同步 + 含结构 + 支持自动建表 + 未显式选择时默认 `smart`；仅数据时无论状态里残留什么都按已有目标表）；`DataSyncModal.tsx` 的策略联动、下拉/「创建索引」可用性改用该判断，文件行数净增 0；两条同步入口说明文案同步更新（六语言）。后端无需改动：引擎按 `content` 判定是否允许改结构。
- 未改：新版任务工作台（`DataSyncWorkbench`）的 `reconcile`（由数据比对生成的同步任务）仍固定 `content=data` + 已有目标表，如需同样放开需另行设计。
- 验证：`tsc` 通过；`dataSyncTableCreation.test.ts`、`dataSyncRequest.test.ts`、DataSyncModal 相关与 i18n 测试通过；未在浏览器里走完整同步流程（需要真实/模拟连接与能力探测）。

### 3.3 补充：数据对比生成的同步任务（对账 / reconcile）可选「自动补字段」（用户已确认：可选开关，默认关）
- 现状：数据对比本身只读（只列出缺失字段、结构差异并生成修复 SQL）；由它生成的对账任务内容固定为「仅数据」，结构选项只给「迁移」类任务，目标缺字段时预检直接报「目标表缺少同步所需字段」，而提示里说的「启用自动补列」在这类任务上没有入口。
- 实现：任务编辑页对快照型对账任务开放「自动补字段」选项（默认关，不改变现有任务；仍不提供「创建索引」/建表）；`buildDataSyncJobEngineConfig` 对「对账 + 开启自动补字段 + 非显式字段映射」的任务让引擎按结构内容（`both`）运行，目标表策略不变（默认 `existing_only`，不建表）；显式字段映射仍保持仅数据（引擎拒绝显式映射 + 结构内容）；预检的「缺字段」「不可自动修复的结构差异」与运行时对齐（开启后缺字段为「将自动补齐」，类型/可空性不一致仍拦截；显式映射不被结构差异拦截）。新增 `dataSyncJobStructureSyncEnabled`。

## 5. 风险与后续
- 放宽后目标列声明长度是源的 4 倍（有告警说明）；`char(n)` 同样放宽，定长补空格的行为随之变化。
- 若用户目标表是已有的（不是本工具建的），需要按提示手工加宽列。
- 后续评估：Oracle / 达梦目标的 `VARCHAR2(n)` / `VARCHAR(n)` 默认也按字节计（除非实例设为按字符），MySQL/PG 源含中文时有同类风险；本次未改。
- 回滚：删除 `byteLengthWidener` 的三处调用即可恢复原样建表。
